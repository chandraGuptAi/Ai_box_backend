# Shipment report engine: inspection, architecture and delivery

## Repository findings

The backend already contains shipment parsing and deterministic metrics (`app/prompts/shipment_prompt.py`), chart planning/aggregation (`app/charts/`), strict chart shape validation (`app/models/report_schema.py`), matplotlib rendering, and PDF/DOCX generators. PostgreSQL saved-report storage and account-header dependencies are present. No existing durable job queue was found. Existing uncommitted changes were preserved.

Angular is in the adjacent `E:/Office/Bigship-ERP-Adminpanel` repository. Its AI Box module already fetches shipment rows, provides ECharts rendering, and exposes report creation and saved-report screens. The initial backend-only search did not include that repository.

The concrete architectural gaps are:

- Legacy report documents have no required version or account identity. Chart IDs exist, but no compare-and-swap chart operation endpoint exists.
- Legacy export routes accept client-posted documents, rather than requiring a particular saved canonical version. Export consistency after a targeted edit therefore depends on the client sending every updated representation correctly.
- Excel generation is absent in the backend.
- Existing chart prompt support does not provide durable targeted chart editing. Whole-report refinement can regenerate chart collections.
- `X-User-Id` is a caller-supplied identity hint, not authentication. The new endpoints also require a random report capability for read/edit/export. A verified tenant identity from the application gateway remains necessary before production source extraction is enabled.

These are code inspection findings, not a reproduction of every historical visualization failure. Browser rendering defects outside the new panel have not been diagnosed.

## Architecture implemented for the first slice

`POST /api/canonical-reports` accepts up to 5,000 application-supplied shipment records. The narrow initial planner produces CREATE_REPORT with shipment-analysis/chart-management selection, status and courier dimensions, and deterministic narrative provenance. It rejects selected unsupported analytical requests rather than inventing revenue or time-series values. This classifier is intentionally not a general natural-language operation interpreter.

Metadata is validated by Pydantic before workflow documents load. Only two locally reviewed implementations are allowlisted. No document, downloaded skill, AI-generated code or unrestricted SQL executes. Runtime skills live in `skills/`, separately from `.agents/skills` development instructions. Chart management is the requested eleventh skill in the roadmap, with the other report types deliberately deferred.

The canonical report stores identity, version, periods, source scope, metric definitions, KPIs, chart datasets, lineage, filters, validation results and timestamps. Optional tables/narrative/recommendation collections are empty in this slice. Currency metrics are not implemented. Shipment counts and cancellation percentage are calculated in Python with Decimal and explicit denominator rules. Unknown status remains distinct from zero and from confirmed failures. Every input record is included; missing dates and unrecognized statuses are counted explicitly. Duplicate-source business reconciliation is not implemented.

The operation engine supports report title editing, adding a chart from an existing validated status/courier aggregation, removing one chart, updating a chart title, changing its type, and obtaining an export snapshot. All declared operation names exist in the validated specification. CREATE_REPORT uses the create endpoint. UPDATE_FILTERS returns a data limitation until authorized extraction is implemented. Axes, labels and series mutations are not yet exposed. ADD_CHART cannot recover an aggregation after its final chart has been removed; it returns a limitation rather than reconstructing data.

Updates use one atomic SQL UPDATE conditioned on account, report capability and expected version. A stale write returns 409. Report reads do not disclose whether an ID exists for another account. Capability plaintext is returned once and only a SHA-256 digest is stored. Production routes reuse DATABASE_URL/PostgreSQL, with parameterized queries and a five-second statement timeout. SQLite is used for isolated automated persistence/concurrency tests. No source SQL is generated by AI.

Angular receives canonical values directly. The adjacent application's new `canonical-preview` component is attached to the existing create screen and uses its already loaded rows. It reuses the existing ECharts component, keeps unchanged chart references, saves each edit on the server, reloads the saved version, and downloads version-bound Excel/PDF. Its sessionStorage capability is scoped by current account to restore the latest preview across browser reloads. This does not add canonical reports to the legacy saved-report listing.

Excel and PDF consume the same saved report. Renderers format values and use chart data without recalculating business metrics. Excel chart labels are explicitly text to prevent spreadsheet formula execution. Excel supports native editable bar, line, pie and doughnut charts. PDF embeds the existing chart renderer output with a canonical data table.

## API contract

1. POST `/api/canonical-reports` with `X-User-Id` and `{records, prompt, source_label}`. Preserve response `access_token` and `report`.
2. GET `/api/canonical-reports/{id}` with the same user ID and `Authorization: Bearer <report-token>`.
3. POST `/api/canonical-reports/{id}/operations` with those headers and, for example, `{operation: "UPDATE_CHART_TYPE", expected_version: 1, chart_id: "chart_status", chart_type: "line"}`. Replace the local canonical snapshot with the response. A 409 requires reload.
4. GET `/api/canonical-reports/{id}/export/xlsx?version=2` or `/export/pdf?version=2`. Download only after matching the displayed version. Removed charts stay absent.

The UI labels these as currently loaded rows. Account-wide completeness, requested date filtering and pagination must not be inferred from a partial input page. `requested_period` and `filters` remain empty rather than claiming the engine applied unavailable filters. The actual data period covers records with valid dates only; missing date counts remain in source metadata.

## Validation and reproducibility

Backend command: `.venv/Scripts/python.exe -m pytest -q`.

`tests/test_canonical_engine.py` independently expects 4 shipments, 1 delivered, 1 cancelled, 1 unknown and a 25.00% cancellation rate from labeled fixture rows. It checks chart totals, lineage, stable IDs, targeted removal/conversion, persistence after a new service instance, concurrent write conflicts, wrong-account and wrong-capability denial, missing-dimension rejection, formula-safe XLSX labels, API preview equality, version-bound downloads and canonical Excel/PDF values. PDF verification independently extracts text with pypdf. This covers API output for Angular; browser behavior is tested separately.

Angular template/type compilation: from the backend, `node ../Bigship-ERP-Adminpanel/node_modules/@angular/compiler-cli/bundles/src/bin/ngc.js -p ../Bigship-ERP-Adminpanel/tsconfig.app.json --noEmit`.

Angular focused browser command: in the frontend, set CHROME_BIN as needed and run `node scripts/test-canonical.cjs`. The focused tsconfig excludes unrelated pre-existing broken specs. The runner also overrides the legacy test target's invalid parent-node_modules stylesheet path. The standard whole-application Angular test target is not claimed to pass.

## Remaining stages and production gates

1. Complete general intent-to-operation planning with clarification and explicit dimension/metric allowlists; preserve the deterministic executor as the only write authority.
2. Integrate verified tenant authentication, authorized paginated application API extraction and approved read-only PostgreSQL source views. Add source adapters for bounded CSV/XLSX uploads with extension/content/ZIP expansion limits, formula/macro rejection, and sensitive-field minimization. Uploaded spreadsheet parsing is not enabled yet.
3. Evaluate a durable queue (Celery/Redis if no suitable application job service is available) for large reports. Specify job ID/state/progress, sanitized failures, retry policy, cancellation, idempotency keys, expiry and cleanup before enabling large jobs. Current synchronous requests are bounded; there is no background-job implementation.
4. Add filter reaggregation and source snapshots, full lineage for new metrics, axes/series edits and canonical-report listing. Add PostgreSQL-specific integration tests alongside isolated SQLite tests.
5. Implement escalation-analysis, courier-performance, financial-analysis, executive-summary, dashboard-builder, custom-report-builder, report-validator, Excel-output-builder and PDF-output-builder incrementally after the shipment slice. The two current exporters are controlled services, not registered output-builder skills yet.
6. Add evidence-checked AI narrative generation, business-finding validation and technical-diagnostic filtering before enabling generated narrative sections. Current new reports contain no generated narrative or technical findings.
7. Add load tests, structured operation telemetry, retention/cleanup, idempotent create handling and full browser-to-live-backend end-to-end tests. Migration/rollout of legacy reports must be explicit; the existing endpoints retain their current behavior.

No production deployment is part of this change. This slice does not establish completion of every acceptance scenario for every legacy report or the full production engine.
